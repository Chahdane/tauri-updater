# Releasing

What a release publishes, what has been proven about it, and what has not.

## The published asset set

A macOS release publishes exactly these, and nothing else:

| Asset | Who reads it | Present when |
| --- | --- | --- |
| `DeltaUpdaterExample.app.tar.gz` | Tauri's updater, on a full download | always |
| `DeltaUpdaterExample.app.tar.gz.sig` | the wider Tauri ecosystem | always |
| `manifest.json` | Tauri's `check()`, and this plugin | always |
| `<old>-to-<new>.zst` | this plugin, direct delta path | a usable predecessor exists |
| `<old>-to-<new>.tar.zst` | this plugin, tar-layer path | a usable predecessor exists |

Nothing from the artifact cache, the tar layer's scratch directory, or
`research/` is uploaded. The upload step names the five patterns explicitly
rather than globbing a directory.

The `.sig` file is not required for updates — the updater reads signatures out of
the manifest — but every other tool in the Tauri ecosystem expects to find one
beside the artifact. It is copied from the manifest rather than generated by a
second signing call, because minisign is randomised and signing twice would put a
different (valid) signature in the file than the one clients check against.

## The three release states

All three are normal. Two of them used to publish nothing (blocker B5).

| | Predecessor | Publishes |
| --- | --- | --- |
| **A** | none — the first release | signed Full-only release |
| **B** | exists, but has no usable artifact | signed Full-only release |
| **C** | exists and is usable | Full + direct patch + tar-layer patch |

Rehearse all three locally, against real `cargo tauri build` output:

```sh
./examples/desktop-app/e2e/build-three-versions.sh /tmp/build
./examples/desktop-app/e2e/rehearse-release.sh     /tmp/build
```

That runs the same binaries with the same arguments the workflow passes, ending
at the same publish gate. Only `gh` is absent.

## Prerequisites

1. **`TAURI_SIGNING_PRIVATE_KEY`** — repository secret. The workflow fails in its
   first step without it.
2. **`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`** — required if the key has one.

   > A key generated with `--password ""` **cannot be read by this tooling at
   > all**. Tauri uses rsign2, which encrypts even with an empty password; this
   > tooling uses the `minisign` crate, which does not. Use a real password.
   > See `DECISIONS.md` #16.

3. The tag is `vX.Y.Z` and matches the app's version. `release-check` compares
   them and refuses to publish a manifest describing a different release.

## The publish gate

Before any upload, `release-check` reads the manifest back as a stranger would
and refuses unless every one of these holds:

- the manifest's version equals the tag being published;
- the document is internally consistent;
- there is a platform entry, and its URL is `https://`;
- every patch URL is `https://`;
- the artifact on disk hashes and sizes to what the delta layer declares;
- the signature verifies against **those bytes** under the configured public key;
- the signature carries an authenticated `delta-v1` identity — not a legacy one;
- that identity's app id, version, platform and digest match the release;
- the tar layer's representation matches what the signature says the artifact is.

Run it by hand against anything already published:

```sh
cargo build --release -p tauri-updater-delta-release
./target/release/release-check \
  --manifest dist/manifest.json --tag v1.2.3 \
  --app-id com.example.myapp --platform darwin-aarch64 \
  --artifact dist/MyApp.app.tar.gz --pubkey "$(cat key.pub)"
```

## Toolchain, and why it is pinned

The tar layer requires rebuilding the published `.app.tar.gz` **byte for byte**,
so anything that changes how that archive is written breaks it.

| Component | How it is pinned |
| --- | --- |
| `tauri-cli` (and the `tauri-bundler` inside it) | `=2.10.1`, an exact version |
| `tar`, `flate2`, zlib-rs backend | `Cargo.lock`, with `--locked` everywhere |
| `tauri-plugin-updater` | `>=2.10.1, <2.11.0` |
| delta backend (zstd) | `Cargo.lock` |
| Rust `std`'s `io::copy` buffer size | **not pinnable** — see below |

The recipe depends on `std::io::copy`'s 8192-byte default buffer, which is a
standard-library implementation detail with no stability guarantee. It cannot be
pinned, so it is *checked* instead: before building anything, the release job
rebuilds a real published artifact from a retained fixture and re-verifies the
original signature against the rebuild. If this runner cannot reproduce a known
artifact, the release stops there rather than publishing a tar layer no client
could use.

That check is the general answer, not a special case for `io::copy`: it fails for
any toolchain drift that would matter, including ones nobody predicted.

## GitHub-hosted transport

Measured 2026-08-14, unauthenticated, against a public release
(`research/experiments/2026-08-14-github-release-transport`):

```text
GET https://github.com/<owner>/<repo>/releases/download/<tag>/<asset>
  -> 302, Location: https://release-assets.githubusercontent.com/...
  -> 200, server: Windows-Azure-Blob/1.0, Content-Length present
```

One cross-host hop, HTTPS throughout, and the CDN URL is signed with roughly an
hour's expiry. Three properties matter to the client and all three are already
handled: the redirect budget (5) covers it, the hop is cross-*host* so a
same-host policy would have broken real downloads, and the chain never leaves
HTTPS — which the client refuses even with the plain-HTTP opt-in enabled.

## What is NOT proven: the hosted end-to-end

**Status: UNPROVEN.**

Everything needed to run it exists —
`examples/desktop-app/e2e/github-hosted-e2e.sh` traces the transport, downloads
the hosted manifests and artifacts, runs the publish gate against what is
actually served, and drives the app with the plain-HTTP opt-in **off**. It has
been executed and correctly refuses to proceed, because the releases do not
exist.

Creating them is the one credential-bound step, and it cannot be done from here:
there is no `gh` CLI, no `GH_TOKEN`, and no `GITHUB_TOKEN` in this environment.
Repository pushes work over SSH; creating a *release* needs the REST API.

**The exact manual step:**

```sh
# 1. A token with `contents: write` on the repository.
export GH_TOKEN=...

# 2. Two prerelease tags. Deliberately non-production names.
git tag v0.0.0-hosted-a && git push origin v0.0.0-hosted-a
#    wait for the Release workflow to finish, then:
git tag v0.0.0-hosted-b && git push origin v0.0.0-hosted-b

# 3. Run the rehearsal against them.
./examples/desktop-app/e2e/github-hosted-e2e.sh \
    <owner>/<repo> v0.0.0-hosted-a v0.0.0-hosted-b
```

The workflow must also have `TAURI_SIGNING_PRIVATE_KEY` set, or step 2 fails
immediately.

Until that runs, the claim "this works over the real distribution path" rests on
the loopback E2E plus the transport measurement above. Those are different
claims, and the difference is deliberately not blurred.

## Apple code signing and notarization

### Two different signatures

Conflating these is the most common way to misread what this project proves.

| | Tauri updater signature | Apple code signing |
| --- | --- | --- |
| Algorithm | minisign (Ed25519) | Apple's CMS over a Developer ID cert |
| Covers | the `.app.tar.gz` bytes | the `.app` bundle's code and resources |
| Checked by | the updater, before installing | Gatekeeper, on first launch |
| Key from | `tauri signer generate` | Apple Developer Program |
| This repo has | **yes**, demonstrated | **no** — no Developer ID |

Everything demonstrated here is the first column. **No claim about the second is
made anywhere in this repository**, and the example app is unsigned and
un-notarized.

### Why the delta design is compatible by construction

`tauri-plugin-updater` 2.10.1's macOS install path (`updater.rs:1209`) does this:

```text
bytes -> GzDecoder -> tar::Archive -> entry.unpack() per entry
      -> rename the installed .app aside
      -> move the extracted .app into place  (AppleScript + admin if denied)
```

The important thing is what it takes as input: **bytes**. Whatever Gatekeeper
needs — `_CodeSignature/`, symlinked `Frameworks`, a stapled notarization ticket
— is inside those bytes, and preserving it across an update is entirely a
question of what `tauri-bundler` wrote into the archive and what `tar`'s
`unpack` restores.

The delta path does not change that question, because it reconstructs an artifact
**bit-identical to the full download** and proves it by digest before anything is
installed. The same `install_inner` then receives the same bytes. So:

> The tar layer is compatible with a signed and notarized application exactly to
> the degree that Tauri's own full-download updater is. It adds no new risk to
> the code signature, because the input to the installer is byte-for-byte the
> artifact the publisher signed and notarized.

That is a real argument, not a hope — but it is an argument, and its premise is
that reconstruction is byte-exact, which is *checked* rather than assumed.

### The residual risks, specifically

Two, and both are about the recompression recipe meeting a bundle shape it has
not met:

1. **GNU long-name entries.** A signed bundle has more files and deeper paths
   (`Contents/_CodeSignature/CodeResources`, framework version directories) than
   the unsigned fixtures this recipe was validated against. Paths over 100 bytes
   produce `L`/`K` entries, whose write pattern is **inferred from `tar`'s source
   and never measured** (`DECISIONS.md` #26).
2. **Bundle contents generally.** The retained fixture is an unsigned app. A
   notarized one has a different file set.

Neither can silently ship a broken update. `--require-tar-layer` runs the
client's whole path at release time — apply, recompress, compare digests — and a
recipe that cannot reproduce a signed bundle's archive **fails the release**. The
worst case is a release that has to go out without a tar layer, which is slower,
not broken.

### The external validation gap

A genuinely notarized end-to-end cannot be performed here: it needs a Developer
ID certificate, an App Store Connect API key for notarization, and an Apple
Developer Program membership. None is available.

This is an **external validation gap, not a software defect**. The distinction
matters: nothing in the code is known or suspected to be wrong for notarized
apps, and no evidence has been gathered that it is right.

To close it, someone with Apple credentials would:

```sh
# 1. Sign and notarize as normal for a Tauri app.
export APPLE_CERTIFICATE=... APPLE_CERTIFICATE_PASSWORD=...
export APPLE_SIGNING_IDENTITY="Developer ID Application: ..."
export APPLE_API_ISSUER=... APPLE_API_KEY=... APPLE_API_KEY_PATH=...
cargo tauri build

# 2. Publish two such releases through the normal workflow.
# 3. Run the hosted rehearsal, and additionally assert on the installed app:
codesign --verify --deep --strict --verbose=2 /Applications/MyApp.app
spctl --assess --type execute --verbose /Applications/MyApp.app
xcrun stapler validate /Applications/MyApp.app
```

The third command is the one that would settle it: a delta-updated app that
passes `spctl --assess` is a delta-updated app Gatekeeper will launch.
